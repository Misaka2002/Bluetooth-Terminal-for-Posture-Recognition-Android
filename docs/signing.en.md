# Signing and release guide

[简体中文](signing.md) · [Back to README](../README.en.md)

## What is a long-term signing key?

Android checks an APK's digital signature when installing it and checks its signing identity when installing an update. For this project, which distributes APKs through GitHub, the straightforward approach is to create your own key for the first public release and keep using it for future updates. Keep the application ID and increase the version code for each release.

A key is usually stored in a `.jks` keystore file. It contains a private key and a certificate. The private key signs the APK and must stay secret. The certificate contains the public key and publisher information and is distributed with the APK. Signing verifies the publisher's signing identity and file integrity; it does not encrypt posture records.

Keep the keystore file, key alias, and passwords for the lifetime of the app. You do not need to buy a certificate or register with Google to distribute a signed APK yourself. When you manage the key yourself, losing it normally prevents you from providing compatible updates to existing installations.

The review APK uses a debug key generated by the build tools. It is suitable for development and testing, rather than a permanent public release identity.

## Create a key in Android Studio

For a first-time setup, use the graphical wizard and enter your passwords yourself.

1. Open this project in Android Studio and select **Build → Generate Signed Bundle / APK**.
2. Select **APK**, click **Next**, and choose the `app` module.
3. Click **Create new** next to **Key store path**.
4. Save the file outside the source directory, for example at `D:\AndroidSigningKeys\posture-terminal-release.jks`. Create the parent directory first.
5. Set a keystore password. You can use `posture-release` as the alias. Use the same password for the key and keystore for compatibility with Android Studio's signing workflow. Choose a validity of **30 years**; Android recommends at least 25.
6. Fill in appropriate publisher information for the certificate. This information is included in the APK's certificate, so avoid unnecessary sensitive personal details.
7. Click **OK**. You can cancel the remaining wizard if you only want to create a key. To produce an APK, continue and select the **release** build.

Make a separate secure backup of the keystore, such as an encrypted copy on an offline storage device. Keep passwords in a password manager and record the alias and associated project. Do not upload the file, passwords, or screenshots containing passwords to GitHub. Collaborators do not need your password.

The project's `.gitignore` excludes common keystore files, `keystore.properties`, and `signing.properties`. Keeping the actual key outside the source directory remains the best approach.

## Create a key without Android Studio

On the development computer, Zulu JDK 21 is available at the path below. The keystore path is an example; choose a location that suits you and do not overwrite an existing release key.

```powershell
New-Item -ItemType Directory -Path 'D:\AndroidSigningKeys' -Force

& 'D:\Zulu\Zulu21\bin\keytool.exe' -genkeypair `
    -keystore 'D:\AndroidSigningKeys\posture-terminal-release.jks' `
    -storetype JKS `
    -alias posture-release `
    -keyalg RSA `
    -keysize 3072 `
    -validity 10950
```

The validity is in days: `10950` is approximately 30 years. The command prompts for passwords and certificate information. Password characters are not displayed while typing. At the key-password prompt, press Enter to reuse the keystore password. Do not add passwords to the command itself, where they could remain in shell history.

To inspect the certificate and its SHA-256 fingerprint:

```powershell
& 'D:\Zulu\Zulu21\bin\keytool.exe' -list -v `
    -keystore 'D:\AndroidSigningKeys\posture-terminal-release.jks' `
    -alias posture-release
```

This displays certificate details without exporting the private key. On another computer, replace the executable path with that computer's JDK path. A keystore created this way can also be selected in Android Studio's signing wizard.

## Releasing this project

The application ID is currently `com.misaka.posture`, with `versionCode 1` and `versionName '0.1.0'` in `app/build.gradle`. Future public updates should keep the application ID and signing identity and increase `versionCode`. Changing the visible `versionName` alone is not sufficient.

The project does not store release-key credentials in Gradle. Android Studio's signing wizard lets you select your key locally. Running `:app:assembleRelease` does not automatically apply your release signature; an unsigned output must not be uploaded as an installable release APK.

The installed debug build and a future release signed with your own key have different signing identities and normally cannot replace one another directly. Export important sessions first, uninstall the debug build, and then install the release. Uninstalling deletes private app records. The app currently cannot import historical sessions from exported ZIPs; exports are for archival and external review. Later releases signed with the same release key can be installed as normal updates.

If you publish on Google Play in the future, review Play App Signing and the distinction between app signing and upload keys. GitHub APK distribution does not require configuring Google Play first.
